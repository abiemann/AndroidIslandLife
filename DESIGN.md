# Design

## Responsibilities

- `IslandScreen.kt`: Compose state and native controls; the header and retry/status UI are separate composables with layout regression tests.
- `IslandWebView.kt`: bundled asset loading, URL restrictions, the small notification bridge, and WebView lifecycle/disposal.
- `scene/src/main.js`: scene construction and render-pass composition.
- `scene/src/weather.js`: complete sunny/storm presets applied to the existing ocean, water, fog, and post-processing resources; sunny lighting remains an independent selection.
- `scene/src/FrameLoop.js`: frame pacing, FPS sampling, pause/background behavior, and terminal failure handling, tested without a GPU.
- `scene/src/IslandControls.js`: the touch adaptation over pinned Three.js controls. `cameraConfig.js` is the shared source of camera bounds for implementation and tests.
- `scene/src/grove.js`: deterministic instanced vegetation. Vendored Ultra-Water modules retain their upstream organization and documented local changes.
- `scene/src/canopyClearance.js`: cached static crown bounds and a local vertical correction that preserves zoom distance and viewing angle.

The app has no data layer or background service. Local Compose state is sufficient for pause/light/weather options; a single native preference stores the selected frame-rate limit across launches. The WebView owns one scene/context for its lifetime. Destroying that view releases its renderer context. Resizing disposes the old main render target and resizes the reused effect targets. Adding a ViewModel, dependency-injection framework, or generic scene framework would not address a current responsibility.

## Runtime behavior

The native screen is a single Compose activity. `AndroidView` owns the WebView lifecycle; `WebViewAssetLoader` supplies only bundled scene content through the standard local HTTPS origin. File access, content access, external navigation and network loads are disabled. The JavaScript bridge exposes only ready, failure and FPS notifications. Native controls send only fixed JavaScript calls with boolean, predefined lighting/weather, or validated frame-rate values (30, 60, or null for unlocked).

The renderer reuses the pinned Ultra-Water simulation, island heightfield/terrain shading, shore map, caustics, atmosphere, reflections and post-processing. Procedural vegetation uses instanced meshes. A perspective camera starts at the island overview. One-finger dragging pans along the ground plane at a baseline focus height of 15m; two-finger twisting changes bearing around that focus, dragging both fingers up/down tilts, and pinching zooms. Twist follows the angle between the fingers, not their horizontal movement. `IslandControls` extends two touch-rotation hooks in pinned Three.js 0.186.1, retaining its pinch, pan, pointer capture and cancellation behavior and rebasing two-finger gestures after a third finger leaves. Wrapped angle differences prevent jumps at ±180°, and nearly coincident fingers rebase the bearing. The minimum camera distance is 172.125m in both orientations, with elevation bounded from 22.95° to 54° above horizontal. Both closest distance and lowest elevation angle are 15% below the previous 202.5m/27° limits. Without local clearance adjustment, the closest/lowest camera height is 82.116m and the lowest near-plane edge is 74.682m, above terrain and rocks. Nearby crown bounds provide local clearance: camera and focus translate vertically together, preserving the requested orbit angle, zoom distance, and horizontal pan. The lift blends in before the eye-to-near-plane footprint reaches a crown and returns to the baseline in clear areas. Crown bounds and scratch vectors are prepared once; the check runs on camera changes, not on every animated frame. Recenter restores the island focus and the aspect-appropriate overview. The 10m near plane preserves shoreline depth precision; local canopy clearance protects close views. Native controls sit at the lower left in landscape to leave the island visible.

The grove exposes its actual broadleaf tree positions for deterministic placement of 90 instanced rocks. Rock centers remain above 10m terrain elevation, with a conservative footprint sampled above 8m and a slope limit to keep boulders on gentle inland ground. Placement runs once during scene creation and reuses the original rock geometry and material.

The Storm/Sun action sits immediately left of Recenter; the pair stays together if the control bar wraps in a narrow window. Weather state survives activity recreation and renderer retry. Storm uses stronger FFT wind/swell, larger shoreline surf, overcast haze, and a darker, less saturated exposure target. Lowering the target prevents automatic exposure from cancelling the overcast look. Returning to Sun restores every changed calm setting and the selected daylight/golden sky. A weather change updates existing uniforms and marks the ocean spectrum dirty without resetting simulation time or rebuilding geometry. Spectrum/sky/shadows refresh on the next permitted draw; repeating the current weather does nothing. A paused toggle draws once without advancing time, and background changes wait for resume. There are no new recurring passes, textures, particle systems, or changes to the selected frame-rate limit; increased foam can still change shading cost.

The original multisampled opaque-then-water pipeline is preserved because the water samples the resolved opaque color/depth while writing to the separate multisample buffer. Disabling MSAA in this pipeline would create invalid framebuffer feedback. Capability checks reject devices without the required float support. Context loss displays an error; retry creates a fresh WebView.

Animation requests stop when the activity is inactive or the document hidden. Pausing freezes simulated time but keeps touch gestures and light changes available through requested redraws. Native pause/light settings survive activity recreation. FPS is averaged over actual scene renders and published about once per second, avoiding per-frame Compose updates. The FPS counter opens a native menu for 30 FPS, 60 FPS, or Unlocked (default), with selection persisted through SharedPreferences. FrameLoop keeps at most one pending callback; unlocked renders on every available callback, and capped modes apply the same cadence to animation and input-driven redraws. Deadlines preserve phase even when display refresh is not a multiple of the selected cap. Mode changes reset the measurement window without waking a paused or inactive scene; replaying an unchanged value does not restart timing. Simulation follows elapsed render time, with a 60ms step bound after stalls. Failures stop the loop, report once, and reset FPS; retry creates a new WebView with the selected mode restored. Rendering uses at most 1.1 million pixels, 1.5x device scale, a 256px sky cube, and reduced mesh/FFT/caustic dimensions.

On Android 15/API 35 and newer, the active WebView requests 30 Hz in the 30 FPS mode and the HIGH frame-rate category for 60 FPS/Unlocked, using Android's [view frame-rate API](https://developer.android.com/develop/ui/views/animations/adaptive-refresh-rate). Pause, background, and failure reset the request to DEFAULT. This is a display hint, not a guarantee; Android retains control of refresh and thermal/battery restrictions. No system settings or screen resolution are changed.

## Source and build boundaries

First-party JavaScript uses ESLint and Prettier; Kotlin uses Spotless with ktlint. Vendored code is excluded from reformatting to preserve an inspectable upstream diff. Dependency versions and the Gradle distribution checksum are pinned. Android assets are kept in source so Android-only builds need no Node installation. The separate verification script rebuilds into a temporary directory and rejects any difference from those assets. CI also runs behavior and native layout checks.

The demo APK is intentionally a development build with a debug signature. It is separate from a store release, which would need maintained release signing, device qualification, and release configuration.
